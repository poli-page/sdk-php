---
title: Output handling
description: Receive PDF bytes in memory, as a stream, written to disk, or stored server-side.
---

The SDK gives you four ways to handle a rendered PDF: in-memory bytes, a PSR-7 stream, a write-to-disk helper, or a stored document on the server. Pick the one that matches how your code consumes the output.

## In-memory (`render->pdf`)

```php
use PoliPage\RenderInput;

$pdf = $client->render->pdf(new RenderInput(
    project: 'billing',
    template: 'invoice',
    data: ['invoiceNumber' => 'INV-001'],
));
// $pdf: binary string — write, upload, or return as-is.
```

Best for documents that fit comfortably in process memory.

## Streaming (`render->pdfStream`)

For large PDFs or piping straight to an HTTP response or object store, use `pdfStream()` and let the SDK keep memory bounded. The return value is a PSR-7 `StreamInterface`.

```php
$stream = $client->render->pdfStream(new RenderInput(
    project: 'billing',
    template: 'invoice',
    data: ['invoiceNumber' => 'INV-001'],
));
// $stream: Psr\Http\Message\StreamInterface — read in chunks, pipe to a response.
```

The client's `timeout` bounds the wait for the first byte and then each gap between two chunks, not the whole stream, so a large PDF read at your own pace is not cut off. The wait for the answer's headers and the wait for the first byte share that one timeout, from the start of the download request (with Guzzle and Symfony HTTP Client; a body Guzzle 7 decodes, and a Symfony client whose PSR-7 streams come from another library than guzzlehttp/psr7 or nyholm/psr7, give the first byte a whole timeout of its own; with Guzzle, response headers that trickle in, each gap within the timeout, are reported as a timeout only once they are complete, as PHP's HTTP stream wrapper that reads them bounds only each gap). A stall past it raises `DOWNLOAD_FAILED` (`Failed to download PDF: timeout`), from `pdfStream()` itself or from the read. A body that ends before its announced length raises `DOWNLOAD_FAILED` (`Failed to download PDF: network error`).

With Guzzle, this download goes through Guzzle's stream handler (PHP's HTTP stream wrapper) rather than cURL: cURL options set on your Guzzle client do not apply to it, and it needs PHP's `allow_url_fopen`. `render->pdf()` and `downloadPdf()` still use cURL.

Read the PSR-7 stream directly (or use `renderToFile()`): a PHP stream resource made from it with `GuzzleHttp\Psr7\StreamWrapper` (guzzlehttp/psr7 3.x) cannot report a failed download, and a copy from it can come out short without an error.

## Write to file (`renderToFile`)

The `renderToFile()` free function (autoloaded from `src/render_to_file.php`) streams bytes directly to disk with bounded memory. Parent directories are created automatically.

The bytes go to a temporary file next to the target, renamed into place only once the PDF is complete: if the render, the download or the write fails, the target is left as it was. A file that cannot be written raises `io_error` with the message `Failed to write PDF: <path>: <reason>`: the path you passed (never the temporary file) and the system's own reason, with PHP's full error chained as `getPrevious()`. It has no status and is never retried.

- **Checked before any API call.** An existing target that is not a regular file (a directory, a FIFO, a socket, a device such as `/dev/stdout` when stdout is a pipe or a terminal) fails with `Failed to write PDF: <path>: not a regular file`, and an existing target that is not writable (a read-only file) fails too and is left untouched. Both are judged from the file's attributes, never by opening it. Missing parent directories are created, and the directory must be writable. To write the PDF to a pipe or to stdout, copy `render->pdfStream()` into it instead.
- **Symbolic links.** When the path is a symbolic link (or a chain of them), the file it points to is written and the link stays a link. A relative link is read against the link's real directory, as the file system does. A link loop is `io_error`.
- **Permissions.** An existing target keeps its permission bits. As the rename replaces it with a new file, its owner and group become those of the calling process, its other hard links keep the old content, and its setuid, setgid and sticky bits are dropped. A new file gets your umask's default mode.

A process killed mid-download can leave a `.<name>.<random>.part` file next to the target.

```php
use function PoliPage\renderToFile;

renderToFile(
    $client,
    new RenderInput(project: 'billing', template: 'invoice', data: []),
    './out.pdf',
);
```

## Server-side storage (`render->document`)

When you want the PDF to live on Poli Page's servers (for later download, preview, or thumbnails), use `render->document()`. It returns a `DocumentDescriptor` with `documentId`, `presignedPdfUrl`, and a `downloadPdf()` method.

```php
$doc = $client->render->document(new RenderInput(
    project: 'billing',
    template: 'invoice',
    data: ['invoiceNumber' => 'INV-001'],
));
$pdf = $doc->downloadPdf();
```

`presignedPdfUrl` has a 15-minute TTL. If it expires, call `$client->documents->get($documentId)` to refresh.

## Example

```php
<?php

require __DIR__ . '/vendor/autoload.php';

use PoliPage\PoliPage;
use PoliPage\RenderInput;

use function PoliPage\renderToFile;

$client = PoliPage::client($_ENV['POLI_PAGE_API_KEY']);

renderToFile(
    $client,
    new RenderInput(
        project: 'billing',
        template: 'invoice',
        data: ['invoiceNumber' => 'INV-001'],
    ),
    './invoices/INV-001.pdf',
);
```
